# NEXAH Observed-Evidence Testkit

Status: Phase V contract and repository layout; implementation pending

## Purpose

This testkit prevents illustrative fixtures, benchmark computations, declared
scenarios, and observed outcomes from being treated as the same kind of
evidence.

Its governing rule is:

> **NO OBSERVED OUTCOME → NO EPISODIC MEMORY UPDATE**

The implemented
**[Orientation Brief contract](../../ARCHITECTURE/orientation_layer/ORIENTATION_BRIEF_CONTRACT.md)**
already enforces the outcome-status/episode-reference boundary. The broader
testkit schemas and external observed-evidence validator remain pending.

## Evidence classes

| Class | Meaning | Example |
|---|---|---|
| `illustrative_fixture` | authored input used to explain behavior | synthetic network JSON |
| `benchmark_model` | published or standard reference model | IEEE/Pandapower network |
| `computation_result` | reproducible output of declared software | solved voltage or convergence failure |
| `observed_measurement` | externally acquired measurement | timestamped bus measurement |
| `observed_outcome` | independently recorded result after orientation | documented post-event system outcome |

Evidence classes describe provenance; they are not quality scores. A benchmark
can be excellent evidence for software behavior while remaining insufficient
for claims about an operational grid.

## Required records

### Case manifest

- case identifier and research question
- evidence class and source
- license and redistribution status
- acquisition or generation procedure
- time and entity semantics
- transformations and exclusions
- predeclared development/evaluation split
- supported claims and forbidden interpretations

### Observation record

- observation identifier
- source and timestamp
- variables, units, and topology identity
- missingness and quality notes
- adapter configuration
- checksum of immutable input

### Scenario record

- scenario identifier
- baseline reference
- explicitly authored change
- reason for the scenario
- declaration that it is not an observation

### Computation result

- input and configuration references
- software and dependency versions
- deterministic seed where relevant
- success, failure, or indeterminate status
- output checksums
- numerical warnings and uncertainty

### Observed outcome

- outcome identifier
- independent source and timestamp
- relationship to the prior observation
- measurement method and uncertainty
- evidence that the outcome was not generated by the tested model

## Outcome firewall

An episodic-memory update is rejected unless all conditions hold:

1. the record type is `observed_outcome`
2. the outcome follows the orientation timestamp
3. the outcome has independent provenance
4. observation and outcome scopes are compatible
5. the orientation report references only evidence available at orientation time
6. no evaluation outcome influenced method or parameter selection

`ScenarioRecord` and `ComputationResult` never pass this gate.

## Validation output

The validator will return one of:

- `accepted_benchmark_record`
- `accepted_observation_only`
- `accepted_outcome_linked_case`
- `rejected`
- `indeterminate`

It will never upgrade an evidence class automatically.

## Showcase rule

A public case card must display:

```text
QUESTION
OBSERVED OR GENERATED INPUT
COMPUTED RESULT
ASSUMPTIONS
MISSING INFORMATION
OUTCOME STATUS
SUPPORTED CLAIMS
NOT SUPPORTED
REPRODUCTION COMMAND
```

This makes the limits part of the invitation: users can see what works, what is
open, and where a contribution would matter.
